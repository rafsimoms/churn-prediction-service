# Churn Prediction Service

Проект полного цикла, представляющий собой продакшн-сервис предсказания оттока клиентов телеком-компании.

## В контексте бизнеса

Существует проблема, что привлечение клиента дороже удержания существующего, поэтому компания теряет деньги каждый раз при уходе клиента.

Продукт этого проекта помогает тем, что выдает ранжированный список клиентов с высоким риском ухода и причинами риска по каждому, соответственно отдел удержания может пытаться сохранить этих клиентов.

## Экономика

Раздел нужен для обоснования решений в подборе порогов, тенденции верны, но цифры выдуманы.

| Параметр | Значение |
|---|---|
| Стоимость удержания | 1 000 рублей |
| LTV уходящего клиента | 15 000 рублей |
| Конверсия удержания | 30% |

Тогда попытка удержать уходящего клиента ожидаемо приносит 0.3 × 15 000 рублей − 1 000 рублей = 3 500 рублей, тогда как попытка удержать лояльного несет за собой ожидаемую потерю 1 000 рублей. Если же уходящего клиента пропустить, компания упускает ожидаемые 0.3 × 15 000 рублей = 4 500 рублей. Таким образом, пропуск уходящего клиента в 4.5 раза дороже ложной тревоги, поэтому модели выгодно перестраховываться, и порог классификации будет ниже стандартных 0.5.

## Датасет и данные

Решать эту задачу я решил на данных Telco Customer Churn, взял их на [Kaggle](https://www.kaggle.com/datasets/blastchar/telco-customer-churn).

В качестве архитектуры исключительно в целях практики и демонстрации навыков SQL я решил хранить данные в реляционной БД(PostrgeSQL) и работать с ними оттуда, доставая их для всех нужд SQL-запросами.

Все данные, в том числе train/test/prod_stream сплит хранятся в одной БД, что является компромиссом для упрощения.

Архитектура БД следующая: 7 таблиц (customers, contracts, services - длинный формат для всех услуг, charges, churn_labels, splits, prod_stream) с единым PK и FK: customer_id. Первые пять таблиц содержат все данные датасета, 
таблица split содержит индикатор train/test/prod_stream для каждого клиента, таблица prod_stream содержит индикатор клиента с измененными данными для будующей симуляции дрефа данных. 

В связи с таким хранинем при каждом SQL-запросе джойнится таблица splits и выбираются строки WHERE splits.split = 'split'. 

Тест используется только на итоговой валидации, prod_stream только в мониторинге дрейфа.
